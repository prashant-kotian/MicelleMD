# MicelleMD Roadmap

Working plan, consolidated from PhD project discussion (2026-09-01/02). Not started yet — this captures the scope and design decisions already made so nothing gets lost before work actually begins, following completion of Paper 3.

## Objective

SurfactantKit computes CPP and aggregation number as **closed-form geometric estimates** from Tanford's tail-volume/length formulas — a fast, analytical approximation, explicitly documented in SurfactantKit itself as "a geometric estimate, not a substitute for aggregation numbers measured directly." MicelleMD is the real-computation complement: *simulate* the same surfactant self-assembling and measure aggregation number, shape, and packing directly from the simulation, rather than estimating it from a single-molecule geometric argument.

This directly strengthens the Paper 3 thesis too: it demonstrates the distinction between "AI recalling/estimating a number" and "actually running the physics" using the project's own tooling as the worked example — SurfactantKit's *estimate* vs. MicelleMD's *simulation* of the identical physical quantity (aggregation number) is a clean, citable illustration of exactly the gap Paper 3's benchmark is built to measure.

## Planned technical approach

- **Method**: coarse-grained MD, MARTINI-style force field (not atomistic — computationally tractable for self-assembly timescales, standard choice in the surfactant-CG-MD literature).
- **Engine**: thin wrapper over an established MD package (GROMACS or OpenMM) — deliberately not a from-scratch MD implementation. The scientific/engineering contribution is the surfactant-specific topology generation and analysis layer, not the integrator.
- **Topology generation**: automated construction of CG surfactant topologies for the surfactant classes already central to this PhD's work — single-chain ionic/nonionic, gemini (two-tail, spacer-linked), and amidoamine-derived architectures specifically (the amide linkage and its hydrogen-bonding behavior is a nontrivial CG-mapping decision worth getting right, not a standard case the usual MARTINI surfactant library covers off the shelf).
- **Simulation**: self-assembly runs starting from random/dispersed initial configuration, standard approach for observing spontaneous micellization in CG-MD.
- **Analysis outputs**:
  - Aggregation number distribution (not just a single mean — real micelles are polydisperse, and reporting the distribution rather than a point estimate is itself a more honest comparison against SurfactantKit's single-number geometric estimate)
  - Micelle shape descriptors: radius of gyration, asphericity/eccentricity
  - Solvent-accessible surface area (SASA)
  - Counterion association/binding degree (a real-computation cross-check against SurfactantKit's `counterion_binding_degree`, which is itself a conductometric-slope-method *estimate*, not a first-principles calculation — same "estimate vs. simulate" comparison pattern)
- **Comparison hooks**: explicit, built-in comparison utility that runs the *same* surfactant through both SurfactantKit's geometric aggregation-number estimate and MicelleMD's simulated result, reporting agreement/disagreement — this comparison IS a core planned deliverable, not an afterthought.

## Open design questions (to resolve when work starts)

- Exact CG mapping scheme for the amidoamine amide linkage (standard MARTINI bead types may not cleanly represent amide hydrogen-bonding behavior — may need a validated custom bead assignment, itself worth literature-checking before hardcoding, per this project's established "verify before hardcode" discipline).
- Which specific surfactants to validate against first — likely reuse the same literature-validated systems already in SurfactantKit's `literature_validation_notes.md` (e.g. SDS, DTAB, CTAB) where independent real aggregation-number measurements already exist (Bales et al. 1998's ~44.8-54.2 range for SDS is a ready-made validation target).
- Compute resource planning — CG-MD self-assembly runs are far more compute-intensive than anything in SurfactantKit; needs its own resource/timeline plan before committing to a run schedule.

**2026-09-03 (later same day) — real bug found and fixed in the cross-type nonbonded scheme above, before it got far: `NonbondedForce` per-pair exceptions ignore the cutoff distance.** The original fix used `addException()` to override cross-type LJ per particle pair — correct idiom for a small, fixed set of special pairs (e.g. 1-2 bonded exclusions), but OpenMM exceptions are evaluated directly regardless of distance, so every cross-type pair in the *entire* system (not just nearby ones) got a permanent, always-on LJ interaction. Found while building a production-scale system with explicit water (see below) and cross-checking its `CustomNonbondedForce`-based scheme against the exception-based one on an identical small system: energies disagreed by ~0.2-0.3%, small enough to be tempting to wave off as noise. Root-caused properly instead: enumerated the actual exceptions OpenMM had stored (`NonbondedForce.getExceptionParameters()`) and checked each one's real particle separation against the 1.1 nm cutoff — **16 of 24 exceptions on a small 2-molecule/11-bead test system were for pairs already >1.1 nm apart**, and a fully independent hand-calculation (no OpenMM force objects at all, raw pairwise LJ + reaction-field Coulomb) confirmed the `CustomNonbondedForce` answer was the physically correct one, not the exception-based one. Fixed by replacing exceptions with one `CustomNonbondedForce` (per-particle type index + `Discrete2DFunction` lookup table, OpenMM's standard "NBFIX"-style mechanism, evaluated via its normal cutoff-respecting neighbor-list code) for LJ, plus a separate charge-only `NonbondedForce` for Coulomb — `build_openmm_system()` and the new `build_solvated_openmm_system()` now share this one correct scheme via `_make_nonbonded_forces()`. Also found and fixed a second, smaller issue in the same pass: `CustomNonbondedForce` defaults to no analytic LJ long-range/dispersion correction, unlike `NonbondedForce`, which defaults to including one (~0.3% of the original discrepancy) — now explicitly enabled to match standard MD practice. `examples/verify_solvated_system_energy.py` is the regression test that catches this class of bug going forward, kept as an ongoing check, not a one-time bug report.

**2026-09-04 (later, major) -- real bug found in the CG route's own nonbonded force setup: directly-bonded (1-2) pairs were never excluded, invalidating the CG production results reported above.** Found while doing the "build an actual GROMACS topology, cross-check against OpenMM" step named earlier in this roadmap -- a hand-built, real-MARTINI-3-parameter GROMACS `.itp` for the exact same 20-molecule smoke-test system (identical topology, identical deterministic grid coordinates) gave a wildly different LJ energy than OpenMM: GROMACS `-7.4 kJ/mol` vs OpenMM `+1175.7 kJ/mol`. Root cause, confirmed by direct fix-and-reverify rather than assumed: `_add_molecule_particles()` in `cg_model.py` adds each bond to `HarmonicBondForce` but never excludes that same pair from the nonbonded LJ (`CustomNonbondedForce`) or Coulomb (`NonbondedForce`) forces -- standard MD practice (and real MARTINI's own `nrexcl=1` convention, confirmed against the same `martini_v3.0.0.itp` source this project's real bead parameters were sourced from) excludes 1-2 bonded pairs from nonbonded interactions entirely, since the harmonic bond term alone should govern that pair. Every bond in every molecule was carrying an extra, unphysical LJ repulsion on top of its harmonic term -- e.g. ~59.6 kJ/mol for a single head-tail1 (Q4n-C1) pair, by hand-calculation at the real cross-term parameters (sigma=0.570 nm, epsilon=2.143 kJ/mol) evaluated at the 0.47 nm bond length. Fixed in `_add_molecule_particles()` (`src/micellemd/cg_model.py`): added `lj_force.addExclusion()` and `coulomb_force.addException()` for every bonded pair, immediately after the bond itself is added -- this function is shared by both `build_openmm_system()` and `build_solvated_openmm_system()`, so the fix covers the real production code path, not just the smoke-test builder. Reverified: OpenMM's LJ energy for the identical 20-molecule system dropped from +1175.7 to **-14.3 kJ/mol**, now matching GROMACS's independent -7.4 kJ/mol in sign and order of magnitude (small remaining difference consistent with genuine, correctly-included 1-3 intramolecular contacts, not a further bug). Two new regression tests added (`tests/test_cg_model.py`): one directly checking the exclusion/exception lists match every bonded pair (not just an energy number), one locking in the corrected -14.336 kJ/mol smoke-test energy with an explicit trip-wire against the old +1175.7 value recurring silently.

**2026-09-04 -- vermouth CG-mapping investigation: real finding, redirected rather than forced.** Checked vermouth's actual installed mapping library exhaustively (every `.map`/`.mapping` file, 150+) before writing any code: it is entirely amino-acid/protein-residue and small-neutral-reference-molecule coverage, with zero entries for alkyl chains, quaternary ammonium, amide linkages, or any surfactant/lipid chemistry. Two targeted literature searches for a published MARTINI mapping specific to amidoamine/gemini cationic surfactant headgroups also came up empty -- no precedent exists to build automatic vermouth mapping against, so doing so today would mean inventing bead assignments from scratch dressed in vermouth's file format, not real automation. Redirected to a more honest, higher-value version of the same question: fetched and read Alessandri et al., *Martini 3 Coarse-Grained Force Field: Small Molecules* (Adv. Theory Simul. 2022)'s actual building-block reference Table 1 directly (not a summary) to ground the existing bead-assignment gap in something real and citable. Two concrete findings from that table: (1) `SN1 = -N(-CH3)2` (a branched tertiary amine) is assigned a Regular-size bead, not a smaller one -- this rules out an initial hypothesis (from a general "branched fragments use smaller beads" tutorial rule) that the charged headgroup nitrogen's Q4n assignment might be oversized; no correction needed there, and it's sourced from the correct primary reference (the main Martini 3 paper) regardless, since Table 1 only covers neutral small molecules. (2) No amide entry exists in Table 1, but every analogous carbonyl-adjacent linkage it does list (ester, aldehyde-adjacent) uses an N-type (H-bond-capable) bead, not the apolar C-type -- real evidence that `make_gemini_surfactant()`'s current tail-to-head topology (which has no dedicated bead for the amide linkage at all, going straight from C1 tail to Q4n head) likely misses real chemistry. Documented as a sharpened, citable version of this function's own pre-existing "amide linkage... nontrivial" caveat, not fixed -- adding a real N-type bead needs the same sourced-parameter rigor the original Q4n/C1/W values got, a deliberate follow-up task in its own right.

**2026-09-05 -- the amide-linkage bead gap is resolved with a real, sourced parameter.** `make_gemini_surfactant()`'s known gap (going straight from C1 tail to Q4n head with no bead at all for the amide linkage that gives "amidoamine" surfactants their name) is fixed.
